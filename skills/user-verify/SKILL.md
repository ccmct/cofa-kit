# 내가 하는 검증 (PV)

AI가 만든 테스트를 AI가 통과시킨 것은 사용자의 검증이 아니다. 아래 순서로 **사용자가 판단할 수 있는 검증 자료**를 만든다. 이 단계에서는 코드를 고치지 않는다.

0. **실행 안내대로 다시 띄우기**: 첫 항목은 사용자가 새 터미널에서 실행 안내 문서의 명령을 그대로 따라 해 서버를 띄우는 것이다. 사용자에게 명령을 알려 주고 결과를 기다린다. 안 뜨면 문서를 고칠 대상으로 표시한다.
1. **기준 목록**: WORKLOG의 요구사항(R번호)과 담당자 답을 모두 나열한다. 하나도 빠뜨리지 않는다.
2. **사용자 기준**: 사용자에게 담당자 말에서 직접 고른 기준을 하나 이상 받는다. "담당자가 ○○라고 했으니 ○○가 ○○여야 한다" 형태로 표에 넣는다. 사용자가 정한 기준이라고 표시한다.
3. **기대 결과 구하기**: 항목마다 기대 결과를 **원본 데이터와 담당자 답에서 직접** 구한다. 작성한 코드나 함수를 쓰지 않는다. 계산 과정(어느 행, 어느 값, 어느 기준)을 한 줄로 적는다.
4. **실제 결과**: 앱을 실제로 실행해서(화면, curl, 테스트) 결과를 얻는다.
5. **비교**: WORKLOG "PV 검증표"를 채운다. 칸은 요구사항·담당자 답 / 확인 방법 / 기대 결과 / 실제 결과 / 일치 / 내가 직접 확인.
6. **다른 방법으로 한 번 더**: 가장 중요한 결과 하나는 코드와 다른 방법으로 확인한다. 예: 원본 파일에서 해당 행만 골라 직접 세기, 손 계산.
   - 지켜야 할 규칙이 여러 개인 결과(배정, 일정, 한도 등)는 **결과 파일만 읽어 규칙을 하나씩 검사하는 작은 검사기**를 따로 만든다. 계산 코드의 함수를 가져다 쓰지 않는다. 규칙마다 위반 수와 위반 예시 몇 개를 출력한다. 검사기도 제출물에 포함하고 실행 방법을 실행 안내에 적는다.
7. **경계와 장애**: 경계값(기준과 같은 값, 기간의 시작과 끝), 빈 값, 잘못된 입력, 재시작을 최소 하나씩 확인한다.
8. **훑어보기**: 결과 전체를 표나 그림으로 볼 방법을 하나 알려 준다. 튀는 값, 한쪽으로 몰린 값, 한눈에 이상해 보이는 것(지나치게 크거나 작은 값, 비어 있는 곳)이 있는지 사용자가 눈으로 본다.
9. **사용자 확인 항목**: 미리보기에서 사용자가 **직접 눈으로** 확인할 항목 2개와 보는 방법(주소, 어디를 보면 되는지, 기대 화면)을 알려 준다. 로그인이 있으면 하나는 실제 미리보기에서 로그인 → 새로고침 → 다른 역할로 확인하는 것으로 한다. 로컬 테스트와 미리보기 환경은 다를 수 있다.
10. **보고**: 일치하지 않는 항목을 맨 위에 둔다. 각각 원인 후보와, 그것이 코드 문제인지 현장 규칙이 애매해서 생긴 문제인지(→ 담당자 확인 필요, 확인 대기로 기록) 구분한다. 고치기 전에 사용자의 결정을 기다린다. 고친 뒤에는 표 전체를 다시 확인한다.

사용자가 "미리보기에서 ~를 직접 확인했어"라고 하면 PV 검증표의 "내가 직접 확인" 칸에 사용자 표현 그대로 적는다.
